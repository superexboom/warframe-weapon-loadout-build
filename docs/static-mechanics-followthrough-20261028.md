# 后续静态机制补全（2026-10-28）

前一提交`dc0036d`已完成连续震地、原生初始连击恢复和Cortege的蓄能/爆炸合同；本页记录继续追原生消费者后的补充，避免将“本轮未追完”混写成“只能游戏实测”。

## Deconstructor / Prime轮换弹体

原生初始化索引为0；每次实际创建投射物先取当前条目，再递增并按列表长度回绕。因此发射顺序为**冲击→穿刺→切割→循环**。普通版每弹130，Prime每弹160，原始触发率25%。原模型只使用第一条Impact，现已修复。

数据保存在`companion-projectile-sequences.json`；每次应用MOD之前选择源伤害类型及投射物身份，让物理MOD、元素基数和状态权重按该弹体计算。两个引擎都在战斗状态和模型缓存键中保存相位；目标死亡和装填不重置相位。版本门控`COMPANION_PROJECTILE_SEQUENCE`防止旧原生核心漏算。

普通合法装备每次发射1枚，按准确相位执行。原生在实际生成的每一枚上推进索引，额外多重尤其分数多重会改变未来相位；暂不把单相位伤害乘期望多重当作完整序列，异常多重会明确提示且退出原生快捷路径。

独立算例：+100%切割、关闭状态/暴击，六次发射是`I,P,S,I,P,S`，普通版总伤`2×(130+130+260)=1040`，Prime`1280`。对260HP目标，普通版六发应杀4个目标；若错误地在死亡后归零只能杀3个。测试同时验证Slash能够产生Bleed。

弹跳同目标重复命中、回收时间、最多3枚在场限制的再发射时序仍单独标记，不宣称此武器全部机制完成。

## Angstrum / Prisma：满蓄力齐射已接入

原始native函数离线执行40个蓄力算例、10个归一化门控对照、20个状态消费者检查，追到了实际逐枚创建循环和弹体保存的伤害因子。当前保留构建的raw MaxCharges=120（Prisma继承）使charge-damage门控成立，不代表跨版本普遍规则。该合同下满3弹发射3颗，每颗600直击+750爆炸；既增加弹数也增加逐弹伤害，没有再除以3。这是全命中、无额外增益、减伤前的4050条件总和，不是游戏实测DPS。

实现同时处理：

- 完整蓄力等待发生在伤害之前。整数剩余装弹N、无速率增益时，Angstrum等待0.5N秒、Prisma0.2N秒；有增益时除以有效蓄力/射速倍率，再按射速和装填开始下一轮。
- N进入多重MOD查询，再算ADD/SET/百分比：N3、ADD1得到4枚，SET2得到2枚，+120%得到6.6期望枚。不能对base1的已修改结果直接再乘3。
- 每枚直击200N与范围250N独立，源状态归一化分母仍是raw1。Prisma直击约26%，范围原生默认10%，不能互借，也不能除以蓄力弹数。
- 本击实际扣弹以及下一次蓄力命中时间传给击杀归因；基础3弹Angstrum首击1.5秒，下一次为6.0秒（0.5秒射击间隔+2.5秒装填+1.5秒蓄力）。
- 普通mode0与灵化mode1隔离；变身往返、半弹匣、持续伤害在蓄力中击杀目标、首发加成均有独立测试。
- API `benchmarkTimeline.chargeVolley`回显已完成齐射的等待、装填量、弹数、逐弹伤害因子和耗弹。

原生末弹多重门控也已闭环：ordinary charged override绕过LAST_MULTISHOT，UseClipSizeAsDamageMultiplier另有否决；包括只剩1弹时也不把齐射误当Final Fusillade。

完整raw/EXE哈希绑定导入器已落地。全弹命中、提前松手、真实飞行、临时增益同帧快照、弹药效率的整数扣弹方式继续显式标注；模式不再保留已修复的“爆炸遗漏/齐射未建模”。

## Cortege火场：不能复用普通爆炸的全MOD伤害

脚本创建临时副投射物，查询EmbedDeathAttack，读取`baseAmount`并经int32截断写入Element。示例2000.9→2000。原生6组查询路由、4组Lua整数转换、3组Element包构建、4组普通元素share算例已独立验证。

- WEAPON_DAMAGE_AMOUNT进入该标量。
- 普通元素MOD修改DamagePercent；Lua只复制baseAmount，故90%电、冰+电和120%火的普通算例不会把标量从2000变成爆炸总伤。
- Element保持自己的Heat和约70%触发、ProcExtraTime=-3；脚本未复制武器暴击/触发字段。
- UseInstigatorDamageMultiplier默认0，不能每跳重复乘武器基础伤害。
- 中立受害者路径已追加6组原字节验证，总计23组；特殊innate或条件基础值、actor全局damage controller与最终HP特例仍不完整。新增独立研究工具`tools/cortege_field_reference.py`承载单个火场每次有效contact的限定公式，contacts由调用者显式指定，暂未作为通用firefield profile启用。资源Amount40被脚本结果覆盖，不能作为固定每跳40。工具的28项公式/边界/CLI测试不同于23组离线native原始代码验证，均不证明实际tick数量。

接触立即尝试伤害，随后按每目标冷却；默认1秒、缓存严格`last+tick<now`且清理在尝试之后。12秒销毁路径来自脚本。事件化时钟需要说明边界，不能把未知的帧调度伪装为精确0/1/2…序列。

## Fired Up仍保留的精确缺口

OnHit脚本本身在native定时升级过期后不会清零`FiredUpValue[id]`，读取、递增、刷新/重加的路径已确认；Lua缓存表与native定时升级是两条存储路径。但该缓存根的全局身份和OnHit环境复用/销毁生命周期尚未闭环，不能由“脚本没有清零”推断“下一次一定保留”。这仍有静态追查路径，当前保持expiry-resume未验证提示。
