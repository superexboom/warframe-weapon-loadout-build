# 远程、同伴、深度搜索与 GPU 可行性

本轮按用户新范围处理：Tennokai 与 WFSim 近战暂不作为纠正目标；比较集中于远程和同伴武器。Bot 继续以低延迟为目标，不增加深度档的额外邻域搜索，不同步或提交 Bot。没有烘焙或构建便携 EXE；为验证计算修复，重新编译了本地 Rust 计算库。

用户已有战甲双配装形态修改保留。开始时记录了 21 个相关文件的哈希与副本，应用层、前端两个共享文件只加入本轮独立修改，其余相关文件逐一保持原哈希。验证运行在包含这些用户修改的工作区。

## 自动赋能开关

用 Akarius Prime 复现一种确定的失败：旧配置同时有 `autoArcane=true`、`optimizeWithArcanes=false`，后端静默关闭自动赋能，返回 `autoLoadout=null`。这两个开关分别保存，切换武器或恢复旧配装后可能出现，因此看起来像只有部分武器有问题。

现在明确请求自动赋能时启用赋能评分；前端勾选自动选择会同时打开评分，关闭评分则取消自动选择，加载旧配置也恢复为一致状态。API 回归检查选择结果与正常输入相同；独立本地页面实际点击验证了两个方向，临时服务和测试标签页已清理。用户未提供原完整配装，不能断言所有类似反馈只由这个原因造成。

另修复了候选种子的保底语义：一个合法完整配装不能仅因它的卡在新的单卡短名单中被淘汰就丢弃。种子现在按完整候选池重新绑定，保留必选、禁选、容量及数量约束，避免最少填卡数把尚未装满的种子前缀误判无效。该修复也保护赋能筛选已经测出的合法提升。

## 元素紫卡的数学去重

旧代码先对普通 MOD 的元素组合去重，再插入元素紫卡。这会漏掉被紫卡插入位置分开的真实组合；不同父节点又可能重复计算大量等价排列。

现在将紫卡及其实际插入点一起纳入完整元素组合身份，再在构造面板、事件回放之前去重。独立枚举所有槽位排列的测试覆盖三元素、四元素、重复元素和固定紫卡位置，不用实现本身生成参考答案。完整候选的已知种子仍作为合法下界。

在相同当前原生核心上，使用开始时保存的三个旧函数作隔离对照：

| 样例 / fast / 30 秒战斗 | 旧实现 | 新实现 | 原生回放次数 |
| --- | ---: | ---: | ---: |
| Braton Prime 紫卡循环 | 超过 240 秒未完成 | 77.84 秒完成 | 旧已执行 105,346；新完整 34,533 |
| Burston Prime 紫卡基础形态 | 超过 240 秒未完成 | 102.20 秒完成 | 旧已执行 112,912；新完整 45,040 |
| Laetum 控制样例 | 13.30 秒 | 13.32 秒 | 两边均 4,483，分数相同 |

两个慢例的旧搜索被取消，不能声称其最终结果相同或给出完整倍率。这证明新路径能在更短时间完成原来超时的具体请求。上述不是缓存烘焙，也未恢复四小时的整批任务。

## 深度档覆盖

只给 Portable 深度档增加额外工作：赋能最多精搜六项，并允许探索当前配装上暂时落后的赋能；灵化最终候选由两项扩至四项，侦察分数容差由 3% 扩至 15%。最终配装的单卡邻域停止提升后，跨所有可变槽对，用各槽最好的四个替代卡形成最多 256 个合法双卡候选，再按实际事件分数比较。

快速和标准档不进入新增双卡阶段；Bot 不被强制走这些深度选项。这仍是有界启发式搜索，不是穷举所有 MOD、紫卡、路线和赋能。

三个独立小空间验证（Akarius Prime、Braton Prime、Verglas Prime，每个 8 卡选 3、50 个合法组合）中，深度档结果均等于独立穷举最佳。五个真实深度样例的本地得分不低于对应标准档，但参考引擎并不保证同样排序：

| 固定榜单赋能、灵化、紫卡；30 秒 | 标准档 WFSim KPM | 深度档 WFSim KPM | 标准 / 深度秒 |
| --- | ---: | ---: | ---: |
| Laetum，带紫卡 | 38.3774 | 39.5236 | 36.91 / 70.19 |
| Tenet Cycron，带紫卡 | 26.2135 | 28.9752 | 60.71 / 87.34 |
| Akarius Prime，无紫卡 | 10.9924 | 9.8513 | 13.84 / 25.10 |

其余两项本地和参考结果保持相同。Akarius 的本地微小提升在参考模型中变差，因此不会将增加搜索量称作必然提高真实游戏表现。

## Enervate 与概率事件

Tenet Cycron 一套带负触发时间紫卡的固定配装，本地原来给出 20.1088 KPM，当前 WFSim 约 2.36。逐卡消融后，去掉 Secondary Enervate 的两边结果分别为 0.687500 与 0.687460，说明差异集中在赋能交互。

确定的问题是：每个期望数量大于零的 Blast 到期事件都被当作一次确定命中。实际很低概率发生的事件也会占用 1/30 秒触发间隔，阻止紧随其后的真正命中计入高阶暴击重置，使层数虚高。

修复后把状态扩为“暴击层数、已计高阶暴击、该概率分支的最近触发时间”，只有事件发生的概率分支消耗间隔。已经完全过期的时钟对未来等价，可归并，不丢弃概率质量。Python 与 Rust 使用相同规则，独立穷举事件树验证概率与重置计数。样例修正为 **2.55258 KPM**，不再以虚高配装误导搜索；与 Monte Carlo 的残余差异仍保留。

已有游戏脚本 `CritOnHit.lua_B` 的 SHA-256 为 `8fb5ba34befa5577c75a39687209fb0ba41a56943fa0c022690edf825056d46a`，导出分别绑定 `OnHit` 和 `OnSuperCrit`。脚本证据支持事件的独立来源，但没有把静态脚本当作整套战斗机制的游戏实测。此次修复的直接依据是期望数量与事件概率不可混用；其他 Enervate 分组命中及间隔假设继续明确保留。

Rust 的状态累加同时改成有索引且保留插入顺序的聚合，避免反复线性查找。一个没有异常伤害的固定长窗口样例，两版完整结果一致，相邻中位数由 35.2 ms 到 30.0 ms；这只是局部样例。旧原生库没有新的能力标记时，会回退正确的 Python 路径。

## Nataruk 投射物的头部规则

原生游戏包 `2026.08.13.13.24` 中，`OmicrusWavePlayerProj` 与 `OmicrusPerfectWavePlayerProj` 都设置 `IgnoreHeadShotBonus=1`，轻射投射物没有该设置。原模型遗漏了这个逐投射物标志。

现在蓄力与完美射击排除目标自带头部倍率、头部暴击倍率和 Acuity 的弱点伤害加成，同时保留命中头部事件、弱点暴击率与 Deadhead 一类独立头部加成的语义。所有 Python / Rust 直伤、状态、持续评分路径一致。

同一套旧配装本地 **16.9079 → 2.25031 KPM**，当前 WFSim 为 **2.23643**。重新搜索后不再装 Acuity，选择镀层弹膛、致命延迟等；本地 **4.02490**，WFSim **4.07330**。将新配装放到官方 180 秒场景，WFSim 为 **5.44234 KPM**，同一公开领跑条目重算为 **3.52188**。这比较的是当前公开条目，不是 WFSim 在新场景下重新搜索的全局结果。

原生记录文件哈希、解析后数据与差异证据保存在本机 `nataruk-headshot-provenance.json`。没有把同一规则推到未经确认的所有武器。

## 爆炸武器、敏锐与死首

用户补充沙皇等武器在自动配装时选择敏锐和死首的问题。本轮把直击、爆炸、延迟爆炸、子弹接触和子弹爆炸逐项检查。

现有伤害对象已经将爆炸与分裂子弹标为不参与弱点命中；头部／躯干伤害一致，弱点增伤和弱点暴击率被清除，死首的头部额外倍率不进入这些部分。孤立爆炸或子弹击杀也不应产生爆头命中、爆头击杀或灵化弱点充能。这些契约已扩大为多类武器、Python 与原生回放的回归。

进一步找到一个会推高敏锐相对价值的错误：旧参考表将许多投射物爆炸写成 `takes_multishot=false`，于是无论生成多少额外投射物，每次扣扳机只有一份爆炸与子弹组。锁住多重的敏锐几乎不用支付丢失额外爆炸的代价。

修复脚本根据原生投射物所有权和匹配的 `AttackData` / `ExplosiveAttack` / `EmbedDeathAttack` 数额，修正 **51 个组件、43 个模式、41 把武器**：每个实际生成的父投射物有自己的爆炸和子弹组。导入器也修正，避免下次生成再覆盖。命中扫描的 `RadialDamage` / `MultiShotBuffsRadialDamage` 是不同契约，Opticor、Trumna 等显式例外保留；无法匹配原生投射物的模式记录原因后跳过。

回归覆盖 Kuva Zarr、Zarr、Kuva Bramma、Kulstar、Kuva Tonkor、Tonkor、Kuva Ogris、Akarius Prime、Sonicor、Lenz、Prisma Lenz、Stahlta、Zhuge Prime、Acceltra Prime。主爆炸、延迟爆炸、子弹接触与子弹爆炸在弱点修饰前后不变；多重则随实际投射物数变化。

实际 Kuva Zarr、Lv170 钢铁、100% 直击头部、30 秒、自动赋能：

- 快速档仍可能选择 Primary Acuity，14.5866 KPM。这个输入保证每发炮弹直击头部，直击部分可以从 Acuity 获利；其范围部分和子弹没有弱点收益。
- 标准档找到不含 Acuity 的方案：Galvanized Chamber、Critical Delay 等，最终 **18.0000 KPM**，比该快速方案高约 **23.4%**。
- 两者自动赋能均为 Primary Crux；本次条件没有复现选 Deadhead。Deadhead 的基伤层数若由真实直击头部击杀取得，可以作用于爆炸；它的头部额外倍率及触发资格则不能由爆炸冒领。因此不按武器名硬禁整张赋能。
- 另外六把爆炸武器的 100% 弱点快速自动配装全部完成，并检查了最终配装回放与搜索分数一致。部分混合武器仍会选择 Acuity，是当前单目标直击条件下的搜索结果，不代表给爆炸加了弱点倍率。

当前单目标基准假定炮弹直接命中目标，再计算其爆炸，不能等同于只用地面爆炸波及敌人的清场场景。结果必须连同这一条件解释。

## 同伴武器与参考范围

固定当前公开执行资源 engine `3194962a0af7`、WASM `8b7fd3c95320`、data `f8bc96ccab7e`。参考原生库与此前官方 WASM 校验结果沿用；本轮重新确认发布的执行身份未变。所有公开条目重新评估 1,000 次，历史显示分不直接参与比例计算。

同伴测试覆盖 10 把武器、12 个组合（含 2 个紫卡）。虽然官方请求模板写 100% 弱点、瞄准，参考引擎内部对同伴仍强制躯干／不开镜；将请求显式改为 0% 与不开镜，完整评分相同，实际 `headshot_rate=0`。没有给同伴开放赋能。

| 同伴样本 | 30 秒达到参照 95% | 将相同配装放入官方 180 秒后达到参照 95% |
| --- | ---: | ---: |
| 无紫卡，10 组 | 10 / 10 | 9 / 10 |
| 带紫卡，2 组 | 2 / 2 | 1 / 2 |

多个无紫卡公开条目使用相似的较弱起始方案，出现数倍提升不意味着优于 WFSim 的完整搜索。也保留 Verglas 的小幅排序差异及长窗口变化。Deconstructor Prime 没有可取的该公开文件（404），未伪造比较。

远程标准档补测中，两项 Furis 达到 300 秒限制，作为超时保留。深度检查是五个有选择的小样本，不能将其总体比例推广到所有远程武器。旧比较中的 Nataruk 结果已由本轮单独修复后的实验替代；受爆炸多重修正影响的历史结果保留原版本，不能称作最终版本的绝对差距。

## GPU 与后续 Rust

RTX 5080 上执行了可复现 CUDA 原型：直接使用现有 Rust `arrival_kernel` / `fold` 作为 CPU 参照，GPU 每线程处理一个独立状态分布，双精度、关闭 FMA 合并，不使用快速数学。每项 180 次递推，比较完整 11 项分布，全部逐位一致；GPU 时间包括传入和传回。

| 独立候选数 | CPU 中位数 | GPU 往返中位数（两次实验范围） |
| --- | ---: | ---: |
| 1 | 0.013–0.014 ms | 0.267–1.951 ms |
| 8 | 0.090–0.093 ms | 0.331–1.835 ms |
| 128 | 1.36–1.40 ms | 0.410–0.532 ms |
| 512 | 5.50–5.58 ms | 0.410–0.490 ms |
| 2,048 | 21.9–22.4 ms | 0.510–0.642 ms |
| 8,192 | 87.1–89.3 ms | 0.632–0.767 ms |

32 个任务在一次实验接近持平、另一次受调度开销影响更慢。这个原型仅含状态分布递推，不含状态过期、目标伤害、击杀反馈、Python resolver 或完整候选准备。当前真实回放 profile 中相关 pooled 阶段约占 0.4%–10%，即使该算子无限快也不能得到表内倍率的端到端收益。

因此 GPU **在足够大的独立批次上可行**，但本轮没有接成产品默认评分路径，也没有用简化公式替换完整评分。更有价值的下一步结构是让不同配装的状态准备变成可传输的批量数据，保留精确 CPU 最终复评和不支持机制的回退。现有动态回调、事件分支和小批次是实际限制。

本轮已在 Rust 完整实现新的 Enervate 状态模型及 Nataruk 规则，并将状态聚合由线性查找改为索引查找。核心评分热点大多已在 Rust，继续迁移应按 profile 的剩余 Python 准备成本选择，不能以迁移代码行数衡量性能。

开发原型入口：`tools/probe_gpu_status.py --simfleet-root <只读 simfleet 目录> --nvrtc-dir <NVRTC DLL 目录> --output <新实验目录>`。它编译隔离的小型 Rust 测试库和 CUDA 原型，不改生产引擎、不暂停 simfleet。当前是 Windows/NVIDIA 研究工具，没有新增运行时依赖。

最终全量 **1,318 项测试及 12 项子测试通过**，耗时 1,616.76 秒，见 `regression-final.log/xml`；在测试收集后新增的导入器 **3 项另行通过**。具体组件回归 74 项、原生／Enervate 相关 61 项、开关和战甲形态 19 项等均有独立记录。前端 JavaScript 语法检查、真实浏览器双向开关检查及运行时 smoke 通过，临时浏览器页面和服务均已清理。
