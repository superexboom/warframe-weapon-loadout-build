# 解算引擎并发重构方案（2026-10-13，待确认）

## 一、现在的「两路」是什么

|位置|现状|后果|
|---|---|---|
|Bot（`service/rarsenal`）|`defaultMaxConcurrent = 2`：2 个常驻 `bot_riven` 进程，一行一个请求，各自串行处理|同时最多算 2 个请求，第 3 个排队|
|每个 Bot 进程 / Portable 服务|首次分析时各自懒建一个进程池（`parallel.get_pool`，min(物理核, 7) 个），每个子进程都加载整份导出数据|2 路 × 8 进程；把并发调到 8 就是 64 个进程，抢核、占内存|
|Portable `app.py`|全局 `ANALYZE_LOCK`，所有引擎计算排队；配装页靠 10-12 加的「交出锁」钩子插队|实际也是两路：一个分析 + 一个配装页请求|
|单个请求内部|进程池只在几个点用：单卡排名（约 200 次）、单词条粗排、束搜索每层、词条贡献；层与层之间的存活者重算、基线、各硬度节点重放都在父进程串行|8 核机器上大部分时间只有 1 个核在算|
|缓存|解析缓存、重放摘要缓存都在各自进程里|子进程之间、请求之间算过的同一个配装互相用不上|
|烘焙|12 个进程各跑一个完整分析，每个再带自己的池|进程数和内存翻倍，2.4–2.9 小时|

在后台有负载时测了一次：已有缓存的 ultra 请求（Soma Prime）5.5 秒里，九成采样时间只有不到 1.5 个核在工作。这次只作参考，
后台负载会让数字偏低，正式数字等阶段 0 在空闲机器上重测。结构上的问题不依赖这个数：并发路数固定死在进程数上，
请求内部又有大段串行。

## 二、WFSim 怎么做（对照点）

- 引擎是纯函数库：一次调用传入 JSON、返回 JSON，没有跨请求的全局状态。wasm、Windows、Linux 原生版结果逐位一致
  （docs/WASM.md、CLIENTS.md）。
- 优化器把工作切成「候选 × 赋能」小任务，按批次（宽度 = 线程数 × 4，限制在 16–256）分给共享的工作线程，
  然后按序号收回结果。线程数默认为全部核数减 2，以低于正常的优先级运行，不卡住用户的其他程序。
  每个任务的随机种子只取决于任务本身，与线程数无关（optimizer/src/evaluate.rs、threads.rs）。
- 搜索：
  - 先做规范形去重，只按元素顺序和 MOD 集合区分，等价的排列只算一次；
  - 再用快速计算粗筛：只跑一次的粗筛，在 6.5 万个任务的范围里没有丢掉真正前 100 名中的任何一个；
  - 然后用逐轮减半淘汰。搜索可以随时取消，并给出当前最好的结果（docs/OPTIMIZER.md）。
- 托管侧：一份计算单拆成很多行，由许多客户端的执行通道去领。simfleet 的调度器让多个任务共用一组执行通道，
  按先来先服务，避免一个大任务独占全部通道。

## 三、目标结构

```
请求（Bot / Portable 分析 / 配装页 / 烘焙）
   │  每个请求是一个「协程」：只做编排，需要算的东西打包成任务批次交出去
   ▼
调度器（每台机器一个）── 按请求公平轮转；优先级：配装页 > 聊天请求 > 分析 > 烘焙
   │  取消的请求直接丢弃未开始的任务
   ▼
共享计算池：N 个常驻进程，各加载一次导出数据；N 默认取全部核数减 2，低于正常优先级
   │  任务 = (上下文编号, 候选)；上下文每个进程只传一次、按编号缓存
   ▼
共享结果缓存（重放摘要 → 结果，有大小上限）：所有请求、所有进程都能命中
```

- 进程数固定为 N+1，与同时在算多少个请求无关。Bot 的 `MaxConcurrent` 只控制同时接收多少个请求，不再决定开几个进程。
- 现在父进程里串行的部分（存活者重算、基线、硬度节点重放、MOD 收益、词条贡献）都改成任务，父进程只负责编排。
- 结果按序号收回、每个请求内部按固定顺序合并。我们的解算是期望值模型，没有随机数，所以 N 取 1、4 还是 15，
  结果都应逐字节一致，这一条作为验收硬指标。

## 四、分阶段

### 阶段 0：基准（约半天）

- 把散落在 scratchpad 里的计时和比对脚本（bench.py / compare.py）收进仓库，作为 `tools/bench_engine.py`。
- 统一测三类指标：
  - 单请求延迟；
  - 同时 1 / 2 / 4 / 8 个请求时的吞吐和 CPU 占用；
  - 进程数和内存。
- 用例：8 个 Bot 请求、2 把武器的烘焙，加 Portable 的分析和自动配装。
- 在你机器空闲时跑；在此之前我不会再跑占满多核的测量。

### 阶段 1：引擎纯函数化（1–2 天）

- 清点模块级可变状态：
  - 各类缓存、`optimizer.load_exports` 的猴子补丁、`parallel._WORKER_CONTEXT`；
  - `ANALYZE_LOCK` 实际在保护的东西。
- 缓存要么改成以全部输入为键、多线程或多进程下安全，要么移进调度器。
- 引擎入口统一为两层：
  - `evaluate(上下文, 任务) → 结果`；
  - 请求编排写成生成器，每次交出一个任务批次，拿回结果后继续。
- 验收：与改前逐字节一致，全量测试通过。

### 阶段 2：调度器和共享池（3–4 天）

- `vendor/wfarsenal/scheduler.py`：常驻进程池、上下文分发、公平轮转、优先级、取消（复用现有
  `SearchCancelled` / `liveSeq`）、共享结果缓存。
- 接入方：
  - Portable：`ANALYZE_LOCK` 和配装页的交出锁钩子换成调度器优先级；
  - `bot_riven serve`：一个进程同时处理多个请求，输入输出按请求编号复用，响应可以乱序；
  - 烘焙：烘焙目标作为低优先级请求交给同一个调度器；
  - Go 端 `riven_worker.go`：改成「1 个进程、多路复用」，`MaxConcurrent` 的含义改为同时在算的请求数。
- 验收：
  - 输出逐字节一致；
  - 8 个并发请求下 CPU 占用不低于 85%；
  - 分析在跑时，配装页延迟不比现在差；
  - 进程数恒为 N+1。

### 阶段 3：搜索本身少算（2–3 天 + 需要你拍板）

- 规范形去重扩展到带元素的紫卡：元素组合层很便宜，先算它，按合成后的伤害向量去重，再决定要不要重放。
  现在只覆盖紫卡不带元素的情况。
- 先用静态面板粗筛，再做完整事件重放：
  - 先实测粗筛和完整重放的前 k 名重合度，像 WFSim 测「前 100 名丢了几个」那样；
  - 这一步会改变结果，要你看过数字再决定开不开。

### 阶段 4（可选）：编译核心

- 用 Rust 写重放核心，按以前的估计约 5–8 千行，包括 damage.py 的期望值部分。
- 阶段 2、3 落地后再看还缺多少；如果并发已经够用，可以不做。

## 五、需要你决定的

1. 计算池默认核数和优先级。我建议默认全部核数减 2、低于正常优先级，可以手动调。你经常在后台跑计算，
   这样不会跟它抢。
2. Bot 的进程模型。我建议改成「单进程多路复用」，Go 端协议要跟着改；另一种是保留多进程、共用一个外部池，改动小但多一层进程间通信。
3. 阶段 3 的粗筛会改变结果，先测、再由你决定；阶段 4 做不做。
4. Bot 什么时候同步。这次赋能的改动和以后的重构都动了引擎，Bot 需要重新同步，并全量烘焙一次（约 2.5–3 小时）。

## 六、风险

- Windows 用 spawn 方式起进程，传上下文要序列化：上下文按编号只传一次，任务本身保持很小（现在每个任务约 25 KB，可以接受）。
- 调度器是新的中心组件，出问题会影响所有请求。保留 `WF_ANALYZER_SERIAL=1` 作为串行回退，测试同时跑串行和并行两条路径。
- 共享缓存要设大小上限，避免长期运行时内存越涨越多。
