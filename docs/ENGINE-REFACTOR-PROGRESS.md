### 2026-10-13（续 2）

  内部 map 换成 Fx 哈希（`fx.rs`；IndexMap 迭代仍是插入顺序，结果不变）；`no_status_probability`（每次异常都做几次 CRT `pow`）

  剩下的开销分散（热量链、DoT 逐跳排程、触发源信号），单线程继续抠收益递减。
- **调度器挂死修复**：工作进程意外退出（池损坏）时，原来完成回调在池自己的管理线程里重新提交任务，调用方会永远等下去
  （可复现：工作进程启动即退出，`map_jobs` 不返回）。改为专用调度线程独占进程池，回调只记录结果并唤醒；损坏的池让它持有的任务
  立即报 `BrokenProcessPool`，之后的任务换新池。新测试 `test_a_dead_worker_fails_its_jobs_and_the_pool_recovers`。
- **任务上下文只传一次**：每个评分任务都携带 ~33 KB 的上下文（武器记录、场景、被动、目标），父进程每次序列化、工作进程每次反序列化
  （Lato 分析 1.17 万个任务：dumps 2.3 s + loads 3.5 s）。`parallel.shared(ctx)` 在父进程只序列化一次，工作进程按摘要缓存解码结果，

### 2026-10-13（续 4）：多核并发

空闲机器（9700X，8 核 16 线程）上按工作进程数测（关预算，输出全部与参考一致）。起点：10 进程只有串行的 1.6–2.5 倍，
平均 2.4–4.1 个进程在忙。按池占用采样定位到父进程独自计算的时间（池空闲 38–65%），逐个改成池任务，选择规则不变：

- `_recommend_positive`：组合枚举（无截止时间）和边际贡献的每次 `fit` 互相独立 → 分数作为池任务算，按原顺序取第一个最高，
  胜者在父进程重算一次拿完整结果。
- `_best_fixed`：同一保留数的全部子集作为池任务评分，取第一个最高再在父进程重算（`max()` 的语义）。
- beam 层：幸存者只需选择序列，完整评估只给可能成为新最优的第一名（无元素约束时），每层少 ~15 次父进程评估；
  批大小 16 → 4×工作进程数。
- 爬山（standard/deep）：交换步全部候选并行评分，按原顺序取最后一个严格改进；增加步取第一个改进，并且只把它之前的候选
  记入已试集合（与逐个评估时一致）；串行时仍是惰性逐个评估。
- 工作进程不再开自己的池（`parallel._IN_WORKER`），因为 `_best_fixed` 也会在工作进程里运行。
- **绑核修正**：原来把第 k 个工作进程绑到逻辑 CPU k，假设 0–7 是 8 个不同物理核；实测 Windows 上 0/1、2/3 是同一物理核的
  超线程（两进程绑 0+1 只有单核 1.12 倍吞吐，0+2 有 1.87 倍）。≤8 进程时一半核闲着。现在读真实拓扑
  （Windows `GetLogicalProcessorInformation`，Linux sysfs），每个物理核的第一个逻辑 CPU 绑一个进程；读不到就不绑。

### 2026-10-13（续 5）：池的空档

- **工作进程多花的 CPU 不是缓存冷**：10 进程时工作进程总共做的评估数（≈1.25 万）、重放数（≈1.25 万）与串行几乎相同，

  只在现配装上筛选会漏掉「改变武器」的进化（Laetum 第五级在默认配装上只有 0.38 倍、配装跟上后 1.16 倍），所以
  每个分支取筛选最好的路线 + 前 3 名进侦察（窄 beam 4/16 的快速搜索），侦察前 2 名（第 2 名须在 3% 以内）与默认
  路线做完整搜索；默认路线的决赛是不带种子的原搜索，开关打开后结果不会低于关闭时。两套配装上分数完全相同的路线
  视为等价只搜一次，侦察后再在代表路线的配装上复核，不同就拆开。

### 2026-10-15：最少极化、紫卡极性、部件贡献、Deadhead 原生化、WFSim 全目录差分

**最少极化**（配装页与紫卡分析的「极化 ×N」）：搜索仍按「每张卡都已极化匹配」的容量口径；实际配装只需总消耗不超过容量。
`optimizer.forma_plan` 是逐槽精确 DP：目标依次为极化次数、移动的卡数、容量消耗；带基础元素的卡保持相对顺序（决定复合元素），
锁定槽不动；架势槽（提高容量）和功能槽（降低消耗）的极化作为可选项，只在需要时计入。前端 `minimalFormaPlan` 是同一算法：
填充最优 / 自动配置回填 / 应用紫卡推荐 / 「最少极化」按钮从原生极性重新规划（可调换非元素卡的位置）；手动换卡、升级、
拖动只在超容量时追加最少的极化，不移动卡。去掉了「极化 −/＋」。随机 60 组配装与穷举结果一致（`tests/test_session_20261015.py`）。
Boltor Prime 填充最优：旧逻辑 7 次（每张不匹配的卡都极化）→ 5 次，容量 58/60。

**紫卡极性**：游戏内紫卡只有 Madurai / Vazarin / Naramon（wiki：揭示时随机，洗卡不变），前后端候选从六系改为三系；紫卡槽的极性
图标只在「原生极性 ↔ 紫卡极性」之间切换（之前会循环到 Umbra / 任意等全部类型）；紫卡编辑器加了极性选择；旧配置里的
Zenurik / Unairu / Penjaga 紫卡迁移成合法极性，为它准备的槽位极化一起跟过去。

**紫卡分析负面词条**：负面行禁用只能为正面的词条（元素、融合、穿透等）；4 条全正面时把本行换成可作负面的词条会自动恢复负面，
分析按钮随之可用；切换正负后刷新可选项；配装页紫卡编辑器同样处理（之前负面行可以选火焰伤害，正负切换也不检查）。

**界面文字**：去掉旧配置迁移提示（迁移静默进行，导出 JSON 不再带 legacyModMigrations）；「冻结目录 / 冻结官方档案 / 后端 / 快照 /
离线数据 / schema / OFFLINE」等改成普通说法；自定义防御的生命 / 护甲 / 护盾类型从 RK_* 代码改成中文选项；诊断面板不再显示
搜索参数（beam、候选数）、英文实现备注和内部路径（路径换成 MOD 名，`ultra-profile-*` 等代码翻译成中文）。

**组合枪慢的原因**：不是组合枪。捕月在 24 种握把 × 装填器组合下配卡约 2 秒，和普通副武器一样；带任何赋能也一样——除了
**次要死首（Deadhead）**：所有武器都慢约 4 倍。爆头击杀叠层的赋能让每次评估先跑一次探测、不确定时再跑 16 条「击杀分支」，
而这条路径只有 Python 版（原生内核不接受 `weak_draw`），每次重放 26 ms 对 1 ms。现在探测与分支（固定的黄金比 Kronecker 序列，
常数从 Python 传入）移进 `replay.rs`，影子模式下 4 把武器 × 4 档爆头率 × 2 种触发口径共 32 组与 Python 参考逐位一致。
捕月 + 死首配卡 9.2 s → 2.6 s，Lex Prime 11.6 s → 3.4 s。

**并发搜索**：灵化侦察、决赛和赋能精搜的几次搜索互相独立，`loadout_search._concurrently` 用线程同时跑（最多 3 个，
`WF_CONCURRENT_SEARCHES`），结果按调用顺序取；它们共享的重放缓存与搜索记忆按内容键控，并改成并发安全（`search_combat`、
`search_session`）。同一请求并发与串行结果逐项相同（分数、路线、MOD）；standard 档两个开关都开、无预算限制时提速只有
约 2%–10%（Torid 33.0 → 31.3 s，Laetum 17.7 → 16.9 s，Soma Prime 35.4 → 34.9 s）：单次搜索已经基本占满工作进程，瓶颈在
父进程的 Python 簿记，之前估计的 30% 偏乐观。

**部件贡献（Shapley）**：`/api/part-values` 枚举已装备普通槽 MOD 与紫卡的全部子集（≤8 件、≤256 种，赋能 / 功能槽 / 架势 /
灵化保持当前设置），在 ln(击杀数) 上算 Shapley 值：exp 后是等效倍率，全部相乘正好等于全装 / 裸武器；两两 Shapley 交互给出
配合（>1）与稀释（<1）。Lex Prime 8 件 256 种组合约 0.4–1.1 秒。配装页手动模式「部件贡献」面板，展开或配装变化时计算。
