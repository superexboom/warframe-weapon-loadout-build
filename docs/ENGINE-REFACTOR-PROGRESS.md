# 解算引擎重构：进度

方案：[ENGINE-REFACTOR-PLAN-2026-10-13.md](ENGINE-REFACTOR-PLAN-2026-10-13.md)。范围按 2026-10-13 的决定只做 Portable（Bot 不动）；
核心数做成界面上的全局设置（类似 WFSim 顶栏的算力份额），不写死；能被 Rust 大幅加速的核心部分优先用 Rust 重写。

验收硬指标：`tools/bench_engine.py compare` 全部 `same`（逐字节一致），全量测试通过。
基准统一用 4 个工作进程（`--workers 4`），给用户后台的 8–10 线程计算留出空间；墙钟时间受后台负载影响，以 CPU 秒为主。

**剖析（Lato fast，串行）**：97% 的时间在逐次事件重放 `_trajectory`（12,459 次）。开销分散在整个事件循环上

### 2026-10-13（续 2）

- **原生重放本体**：计数器加了按函数的包含式计时（`wfcore.counters(enable=True)`，默认关，开销为零）。
  内部 map 换成 Fx 哈希（`fx.rs`；IndexMap 迭代仍是插入顺序，结果不变）；`no_status_probability`（每次异常都做几次 CRT `pow`）
  按（视图、类型、瞄准）记忆；`proc-<类型>` 信号名不再每次 `format!`。Boltor 分析里 `add_procs` 16.1 → 9.2 s，原生本体约 23 → 19 s。
  剩下的开销分散（热量链、DoT 逐跳排程、触发源信号），单线程继续抠收益递减。
- **调度器挂死修复**：工作进程意外退出（池损坏）时，原来完成回调在池自己的管理线程里重新提交任务，调用方会永远等下去
  （可复现：工作进程启动即退出，`map_jobs` 不返回）。改为专用调度线程独占进程池，回调只记录结果并唤醒；损坏的池让它持有的任务
  立即报 `BrokenProcessPool`，之后的任务换新池。新测试 `test_a_dead_worker_fails_its_jobs_and_the_pool_recovers`。
- **任务上下文只传一次**：每个评分任务都携带 ~33 KB 的上下文（武器记录、场景、被动、目标），父进程每次序列化、工作进程每次反序列化
  （Lato 分析 1.17 万个任务：dumps 2.3 s + loads 3.5 s）。`parallel.shared(ctx)` 在父进程只序列化一次，工作进程按摘要缓存解码结果，
  同一批任务复用同一个对象（工作进程里按对象身份的缓存也能命中）。无竞争测量（串行执行但每个任务做序列化往返）：43.1 → 37.2 CPU 秒
  （纯内联 33.6）。2 进程下 5 个用例输出与参考一致；Lato 墙钟 32–38 → 26.9 s（同样有后台负载）。
- 测量注意：用户的 simfleet 在所有核上以空闲优先级运行（总 CPU 约 81%），超线程争用让多进程计时偏慢；多进程结论以无竞争测量为准。
- `ANALYZE_LOCK` 暂不去掉：Portable 是单用户桌面程序，现有「分析在心跳处让出引擎给配装页」机制够用；去锁需要原生重放释放 GIL
  （重放中途要回调 Python 解析器），收益只在多个请求同时计算时才有，留给需要多用户托管时再做。
