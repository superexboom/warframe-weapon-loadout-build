# GPU 烘焙结论与时间预算（2026-10-26）

## 决策

**采用 CPU 调度＋GPU 完整候选批量评分；不把当前逐事件的小算子直接搬到 GPU，不迁移实时紫卡求解。** 第一批覆盖可预展开属性、固定形态、有限事件状态的远程武器；复杂投射物、近战、灵化切换、弱点击杀/免费弹药反馈先留 CPU。资格按实际构筑和场景判定，不维护武器名称白名单。

当前正式烘焙仍完全使用 CPU/Rust。已完成的 GPU 代码是逐位验证的数学原型、成本判定和清单工具，**尚无能产出完整 Portable 配装评分的 GPU 后端**，所以当前可兑现的整批 GPU 节时是 0。下面约三小时半是后端落地后的工程预算，不是已经测到的新全量烘焙时长。

以用户约四小时为基线，完整批量评分首期按 **约 3 小时 12 分至 3 小时 46 分、中心约 3 小时 29 分**估算，即节省约 14–48 分钟。规划可先按节省半小时做预算。没有证据支持四小时直接减到一两小时；理想 CPU/GPU 重叠下的下界不作为承诺。

## 可以交给 GPU 的计算与 CPU 的职责

| 环节 | 首期执行位置 | 原因与准入条件 |
|---|---|---|
| 导出/规则解析、候选生成、卡族/容量/极化合法性、元素顺序、缓存索引 | CPU | 控制与数据准备任务；GPU 不适合大量小对象及分支遍历 |
| 基础面板、状态持续 DPS 的廉价筛选 | CPU/Rust | 现成 Rust 路径很便宜；不为一个小分数支付复制、排队和内核调用成本 |
| 无紫卡基线、正面组合、负面重搜、元素/路线候选中的完整战斗评分 | CPU 调度，合格大批次交 GPU | 候选间独立；必须把战斗整段留在 GPU，输出同一 KPM/windowedDps 合同 |
| 同一配装的多个硬度点、独立重复验证 | 合格大批次交 GPU | 当前血量批接口通常只有 6 场，不足以单独喂饱 GPU；应跨候选合并 |
| 负面词条是否继续搜索、阈值证明、排名及下一轮 beam 选择 | CPU | 下一步依赖上一步结果；可批量评估同层候选，但不能任意跨层推测执行 |
| 镀层/CO 等有限状态的属性组合 | 先 CPU 预展开，后交 GPU 查询表 | 禁止 GPU 运行中每变化一次状态就回 Python；超过状态上限自动留 CPU |
| 史特克、守望延迟独立球、沙皇集束、Onos、远程引爆、复杂持续场 | CPU 首期 | 实体生命周期/空间/事件依赖复杂，且测得大量成本在准备层；不是数学上永远不能上 GPU |
| 架势/锤子/战刃等近战调度、灵化循环、弱点击杀或免费弹药分支 | CPU 首期 | 状态组合和反馈路径多，应逐项完成等价移植后再扩展 |
| 小型同伴武器、很短且便宜的任务 | CPU 默认，动态测速可改变 | 例如 Cryotra 两种紫卡结构总共约 5.9 秒，多数时间不是设备计算 |
| 完成分片校验、fingerprint/contextHash、失败恢复、原子合并发布 | CPU 协调进程 | GPU 只返回评分，不自行写生产缓存 |

所有类型仍能由 CPU 烘焙。这里划分的是哪些评分子任务值得卸载，不是宣称一类武器无法缓存。GPU 后端不得换用 simfleet/WFSim 的评分结果来填 Portable 缓存：两套模型目前不同，尤其最近守望对照仍有离散击杀偏差。

## 实际目录和耗时分布

按 `bake-analysis-statics.py` 的真实默认选择枚举 **642 个当前可分析武器任务**，灵化取默认选中形态，默认不打开灵化循环/瞄准；此前试用“全部灵化循环”的初稿 inventory 不用于结论。每档会处理三正面和两正面两套推荐，额外开火模式、更多档位会增加任务量。

| 结构分组（无卡初步分类） | 当前任务 | 能匹配旧进度的任务 | 占匹配旧 worker 时间 |
|---|---:|---:|---:|
| 固定形态候选，需再检查所装卡引入的状态 | 375 | 369 | 49.73% |
| 武器自带有限状态，需额外预展开 | 19 | 19 | 5.72% |
| 复杂状态/实体/近战，首期 CPU | 248 | 247 | 44.55% |

旧记录共 658 个任务，匹配当前目录 635 个、134,481.4 worker 秒，约覆盖旧记录 96.2% worker 时间。旧指纹 `7c2a1b40f5f1f952`，当前 `3f9f649c32743106`；旧进度只用于结构权重，不当作当前单任务速度。分组也不是最终 GPU 放行结果：固定形态装上特定 MOD/赋能后仍可能回退。

## 八个完整任务的当前剖析

同一当前源码与原生库；每个独立进程禁用生产缓存持久化，在内存完成三正面＋两正面。任务使用其真实默认烘焙上下文。没有生成生产分片、没有跑完整目录。计时包含轻量计数器开销，不能与以前未计时的值直接声称倍率提升。

| 武器 / 档位 | 完整两结构 / 秒 | Rust 入口占比 | 其中属性回调＋视图转换占整项 | 状态池占整项 |
|---|---:|---:|---:|---:|
| Lato / fast | 100.91 | 57.5% | 15.6% | 2.65% |
| Torid / fast | 32.97 | 60.6% | 7.2% | 2.98% |
| Cryotra / fast | 5.87 | 37.0% | 28.3% | 0.02% |
| Nikana Prime / fast | 33.59 | 71.6% | 33.4% | 1.65% |
| Kuva Zarr / fast | 44.13 | 75.5% | 60.9% | 0.57% |
| Stug / fast | 156.29 | 82.9% | 69.1% | 0.92% |
| Vectis Prime / fast | 33.75 | 66.5% | 43.2% | 1.34% |
| Boltor Prime / standard | 214.33 | 78.9% | 12.8% | 3.80% |

Rust 入口时间包含回到 Python resolver 及对象转换，不能把“83% 在 Rust”理解为“83% 能直接搬上 GPU”。setup 与 resolver/view 有重叠，因此报告只给扣除后的上下界，不相加重复计时：简单形态 fast 样本的纯运算范围约 34.6%–43.1%，standard 单个样本约 61.7%–66.2%；复杂组约 8.6%–18.2%。这些是选取样本，不是目录随机抽样的统计置信区间。

全部样本合计 621.85 秒，状态池仅占 **2.33%**。哪怕把状态池变成零成本，按四小时锚点也只省约 **5.6 分钟**；真实集成还需搬运和排队，所以不选择“单独把每次 fold 发给 GPU”的路线。属性构造/转换继续迁往纯 Rust 或跨战斗复用，对 Stug/Zarr/Vectis 更值得优先做。

负面重搜占多个样本的大部分时间（例如 Lato 约 84%、Boltor standard 约 60%），但它由大量候选评分组成；不是可以整个跳过的数学开销。应从中收集独立批次，保留现有判定门槛和搜索质量。

## RTX 5080 的设备试验

硬件为 Ryzen 7 9700X（8 核/16 线程）＋RTX 5080 16 GiB，驱动 616.92，compute_120。试验时原有 simfleet 一直运行，GPU 前后显示约 99% 使用率。本轮未暂停其他任务；以下是共享设备测量，不能标成 GPU 独占峰值。保留两轮独立结果以展示调度波动。

CUDA 使用 double、禁 FMA 合并、非 FTZ、精确除法/平方根。对照直接编译当前 Rust `proc.rs`，同时测 1/8/16 条 CPU 工作线程；每一轮核对完整输出逐字节一致。两个内核：

- `status_batch`：原有固定到达分布卷积。
- `pool_batch`：本轮增加两栈概率池，包含到期、变化的到达核、目标重置、每步分布查询；有明确 64 项实验上限，不冒充完整战斗内核。

两轮共 48 组配置，批大小 8/32/128/512/2048/8192，30/180 步，所有 GPU 与单/多核 CPU 输出一致。下面取第二轮 7 次暖态计时中位数，GPU 列包含上传、同步和下载；CPU 列取 8/16 线程中较快者：

| 180 步内核 | 独立实例 | 多核 CPU / ms | GPU / ms | 多核 CPU / GPU |
|---|---:|---:|---:|---:|
| 固定卷积 | 128 | 0.351 | 1.232 | 0.29× |
| 固定卷积 | 512 | 0.862 | 2.802 | 0.31× |
| 固定卷积 | 2048 | 2.935 | 2.124 | 1.38× |
| 固定卷积 | 8192 | 10.965 | 2.734 | 4.01× |
| 含过期/重置的状态池 | 128 | 1.162 | 25.774 | 0.045× |
| 同上 | 512 | 3.933 | 29.541 | 0.13× |
| 同上 | 2048 | 14.120 | 31.911 | 0.44× |
| 同上 | 8192 | 47.268 | 26.357 | 1.79× |

第一轮 8192 状态池为 54.418/31.801 ms，约 1.71×。固定卷积两轮变化更明显，因此不以最好单次推算总量。大量私有状态和分支会吃掉简单卷积的优势；消费级 GPU 的宣传浮点性能也不是当前双精度事件引擎的吞吐。

实际 Lato fast 的 221 个 beam 层共有 24,063 个去重候选，**中位数只有 43，最大 784**；没有一层达到 2048。约 46.4% 候选位于至少 512 个的层。必须做跨任务、跨 worker 的集中批次，或把一批候选的多个硬度点一起提交。将单个 worker 当前串行 `_evaluate` 替换成同步 GPU 调用会变慢。

## 时间估算的算式与条件

使用保守的非完全重叠模型：

`新时间 = 原时间 × [(1 − p×f) + p×f/s + h]`

- `p`：可卸载任务占旧 worker 时间的比例，约 49.7%；增加有限状态编译后上限约 55.5%。
- `f`：这些任务中能留在设备上的计算比例；以样本范围选 35%/50%/60%。
- `s`：该完整设备评分部分相对整组 CPU worker 的吞吐倍率，规划取 1.8/2.5/3.0，**仍需完整候选内核验证，当前只测了子算子**。
- `h`：准备、排队、校验、尾部不足批次等额外成本，暂预留原总量 2%。这也是待验证假设。

| 情况 | 条件 | 四小时锚点的新时间 | 节省 |
|---|---|---:|---:|
| 保守 | p=49.7%，f=35%，s=1.8，h=2% | 3h46m | 14m / 5.7% |
| 中心预算 | p=49.7%，f=50%，s=2.5，h=2% | 3h29m | 31m / 12.9% |
| 扩展首期 | p=55.5%，f=60%，s=3.0，h=2% | 3h12m | 48m / 20.2% |

估算没有叠加以前 CPU 缓存优化的百分比，也没有把旧四小时当成当前源码全目录实测。档位、全部模式开关、任务长尾、同机 simfleet 资源分配都会改变结果。若实际完整内核不达准入收益，留在 CPU，收益可为零。待首期后端完成后，应以固定目录/档位/worker 数的 CPU-only 与 CPU+GPU 同批对照替换这个预算。

## 实施顺序和退出条件

1. **先准备纯数据候选。** 将固定形态需要的 MOD/元素、离散叠层组合编译成有界表；CO 等连续状态预打包当前 CoSpec 解析系数，在设备端按原公式计算，不能用粗网格插值冒充等价。消除设备运行中的 Python 回调。保持当前精度、运算顺序与字段含义；不能删掉状态、延迟分量或击杀反馈来获取速度。
2. **移植完整候选战斗循环。** 第一批只处理已覆盖语义的固定形态，计算全部硬度点；不把 simfleet 的 WFSim 内核当 Portable 的替代评分器。把可复用的 CUDA 驱动、批次队列、版本绑定、探测/回退策略学过来即可。
3. **一个 GPU 协调进程。** 多个 CPU bake worker 提交已准备候选，按目标/机制签名组成有界同类批次；不足批次、等待过久或尾部直接回 CPU。禁止每个 worker 创建一个 GPU 上下文抢资源。
4. **按实际收益准入。** 不固定宣称 512 或 8192 永远最佳；测整批 CPU 与 GPU，成本包括准备、传输、校验、排队，至少 15% 收益才接收。当前原型在共享机器下需要数千实例才有可靠优势。
5. **语义与资源双重回退。** 先逐项 CPU/GPU 分数和排名一致；引擎/数据/设备/驱动/场景变化重测。未知机制、状态表超限、显存不足、超时或差异直接回 CPU。最终候选 CPU 复核，分片仍由原协调进程校验并原子合并。
6. **收尾与资源预算。** 当前 16 GiB GPU 仍有 simfleet 在运行；正式烘焙应明确给 GPU 的资源份额。尾部批次不让 CPU 空等 GPU。首期若固定同批 A/B 节省不足 10%，不扩展到复杂武器，优先继续 CPU 属性准备层优化。

新增 `tools/gpu_bake_plan.py` 固化了成本算式和准入判定：`full_candidate_kernel=False` 时即使微内核再快，也不能获准生成 GPU 缓存。这个模块当前用于方案/测试，不在生产请求路径里。`tools/audit_gpu_bake.py` 可复跑目录与有界任务剖析，`tools/benchmark_gpu_bake.py` 可复跑设备实验。

## Bot 同步与验证

本次 GPU 结论不要求 Bot 接入 CUDA。Bot 继续使用 CPU/Rust 快速求解；此前已确认的伤害、赋能、史特克、守望变形及锤子剑风修正可作为同步批次。GPU 工具留 Portable 的开发/烘焙侧，不进 Bot 在线请求路径；本轮尚未修改 Bot。

本轮只新增/扩展开发工具、数学实验和文档，未修改生产评分引擎、缓存格式、实时求解入口。47 项相关回归通过。八个任务均完成两种结构，未超时；48 组设备配置全部逐位一致。未启动全目录烘焙，未发布缓存，未构建 Portable EXE。

机器可读记录位于 [evidence/gpu-bake-20261026/](evidence/gpu-bake-20261026/)。本机完整目录 `.local/delivery/gpu-bake-decision-20261026/` 保存原始旧进度、编译产物、GPU计时和复现脚本。CUDA runtime compiler 12.9.86 仅安装到该隔离目录，未改系统 Python 环境。所有原有 21 个用户修改路径保留。
