## 实际复用的是哪一种结果

- 完全相同的请求可直接命中进程内的完整答案。不同紫卡，即使武器和静态分片相同，仍要重做当前卡的配装搜索。冷／分片／同进程换卡用同一张受测卡；换卡组先解算一张数值不同的预热卡。输出哈希覆盖实际与无卡配装、推荐、致命负面及其阈值、灵化选项；另检查评估次数、预算未截断及直接命中标记。
- 正常烘焙自动保存共享依赖、武器依赖和分片结果的 SHA-256。共享依赖含实际计算核心和执行模式、评分规则、公共数据、档位策略与分片生产程序。武器依赖既含原始导出，也含补丁处理后的记录和目录条目。已核实按路径取值的三个表是连发、蓄力、每发装填；未知来源或不熟悉的格式按共享依赖处理。
- 升级数据后，未变的完整分片可以改用新版本全局指纹；条目内容和原来的键顺序不变。武器、模式、档位和需要的两正／三正结构都要匹配。只烘过三正的分片不能证明两正已完成。首次升级旧格式需要冷烘一次；已有的普通主缓存不能反推出过去使用的逐武器依赖。
- 引擎或共享 MOD、敌人、赋能、源锁和游戏版本变化，全体失效。当前没有承诺跨游戏构建、跨原生二进制、或按单个 MOD 精确追踪武器；后者还需要完整的候选依赖关系，只有最终配卡不含该 MOD 并不能证明它无影响。

## CPU 优化落点

原生回放复用目标异常快照的存储，减少 Heat 队列和径向部件的重复分配。候选与回放缓存按当前上下文值取键，包括嵌套的目标部位倍率；带进程调试校验的回放不读普通回放结果。缓存发布仍重读源文件，比对的是新读出的字节，只对完全相同字节复用 Python 语法树的计算。目录只需要判定有没有可用 MOD，现在找到第一张即停止；真正的配置搜索仍枚举原有全集。

在同一台 Ryzen 7 9700X 上依次用旧／新／新／旧源码启动，导入应用与建立目录分别耗时 `5.06 / 1.77 / 1.91 / 4.93` 秒。684 条武器目录记录的完整输出哈希一致。另试过向棱晶安格斯壮的负面安全阈值额外提供已知配装：五个阈值点、最多 54 套候选没有多提供一个安全证明，所以没有扩大常规搜索或削减阈值精度。

## 离线受控实验

独立复制 160 个输入文件，仅将毒芽 Prime 主射的 `fireModes[0].damage.critChance` 从 `0.079999998` 改为 `0.28`。这是为了检验依赖的实验改动，未写入正式游戏数据。没有改动时两个分片都能直接续用。改单武器后，棱晶安格斯壮分片不变，毒芽 Prime 的推荐结果实际发生了变化。增量与同一新数据的强制冷烘，两份完整 `entries` 按原始顺序序列化均逐字节一致。

| 两个 deep 目标，外层 2 worker | 进程外墙钟 | 目标 worker CPU 合计 |
| --- | ---: | ---: |
| 增量：重算毒芽、复用棱晶安格斯壮 | 76.63 s | 68.00 s |
| 强制冷算两把 | 96.52 s | 171.92 s |

样本节省 20.6% 墙钟、60.4% 目标 CPU；CPU 不含父进程和 worker 启动。该试验使用中间版本 `ca1a0d364f92addb`。两个新结果的 SHA-256 前缀分别为 `87118dec9edb482a` 和 `c43b33de2561f83c`。按当前 642 个默认 deep 任务做了实际盘点：实验目录只有两份基线，所以当时实际复用 1 份、待算 641 份；若事先有完整 642 份有效基线，同类单武器改动才有条件复用 641 份。更换共享 MOD 后，计划确认为 642 份全算。未将两武器的百分比外推到四小时的全目录烘焙。

最终发布源码又独立做了四次计划校验。两分片原始数据：2 份当前；只改毒芽 Prime 暴击率：重算模式 0、复用棱晶安格斯壮模式 1；只改共享 MOD 文件的空白：两份都重算；只改独立 Arena 模块：两份仍是当前版本。四次 `--dry-run` 均未写分片，原分片哈希不变。逐条目标与指纹见 `.local/cpu-incremental-20261118/release-plan-proof/coverage.json`。

## 复现

```powershell
python tools/build_native.py
$out = '.local/cache'
python tools/bake-analysis-statics.py --profile deep --shard-dir $out --dry-run --report "$out/deep-plan.json"
# 确认计划后选目标，沿用同一目录；加 --force-recompute 可以强制冷算做对照。
python tools/bake-analysis-statics.py --profile deep --workers 2 --shards-only --shard-dir $out --weapon /Lotus/Weapons/Tenno/Pistols/PrimeZakti/PrimeZaktiPistol --weapon /Lotus/Weapons/Corpus/Pistols/CrpHandRL/PrismaAngstrum
python tools/bench_engine.py cache-states "$out/request-latency.json" --shard-dir $out --weapon 'Prisma Angstrum' --weapon 'Zakti Prime'
```

`--dry-run` 只读取已有分片；报告另列 `pendingTargets`、`reusableTargets`（武器路径及模式），以及当前版本可直接续用的数量。常规烘焙只有完整通过校验才会合并主缓存。归档、迁移目录和旧分片边界见 [README](../README.md#增量烘焙缓存)。

本机只读实测记录在 `.local/cpu-incremental-20261118/`：`release-deep/report.json` 是最终两分片冷烘，`release-abba/report.json` 是完整请求，`release-abba/shard-parity.json` 是内容哈希，`sandbox-validation/validation-report.json` 是增量与强制冷烘的比较。另用真实空战武器 fast 分片测试 `save → restore`，恢复文件哈希与原分片完全相同，正常烘焙判定为已完成。源码与打包暂存目录实际加载的原生库指纹相同；本轮没有生成全目录缓存或发布 EXE。
